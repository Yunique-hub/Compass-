# Compass Skill 3.3.0 易思捷平台测试报告

## 1. 结论摘要

Compass Skill 已从 3.2.0 升级并正式发布为 3.3.0。本次最关键的兼容性修复已经生效：3.3.0 使用与平台参考样例一致的“单一同名顶层目录”ZIP 结构后，易思捷运行容器可以正常读取主 `SKILL.md`、领域参考资料和 `knowledge/platform-runtime.md`，3.2.0 的运行时 404 不再出现。

5 组平台用例证明，预算规划、疲劳降载、事实门禁、负例路由和知识资源读取的核心逻辑均可工作。其中预算规划从 3.2.0 的错误结果修正为总量严格等于 10 小时，疲劳场景可以自动触发并降至 4.5 小时、1 个核心任务，未经核验的市场信息没有编造薪资数字或趋势，简单知识问答没有误调用 Compass。

当前不能把 3.3.0 判为“所有验收项完全通过”。5 组响应都出现了英文内部分析或 `</think>`，自动安全校验均失败；参考物理实验 Skill 也出现了同类泄漏，因此这是可复现的平台输出链路问题，不是 Compass 业务规则独有的问题。此外，平台日志证明脚本文件可以被读取，但没有形成可靠的“脚本实际执行成功”证据，不能把读取脚本表述为已经执行机器校验。

综合判定：**3.3.0 已达到可在平台正常加载、调用和完成核心任务的发布目标；作品呈现与数据安全仍受平台思维链泄漏影响，发布状态为“核心功能通过，平台输出安全待修复”。**

- 主逻辑：识别任务、调用资源、执行处理、输出结果的短链路
- 资源组织：`knowledge/` 存放知识文件，`scripts/` 存放可调用脚本
- 平台回下载包与用户提供 ZIP 的 SHA-256 完全一致
- 平台运行容器成功读取 `/mnt/skills/custom/physics-ai-experiment-assistant/v1.0.0/SKILL.md` 和 `knowledge/` 资源
- 参考 Skill 的平台输出同样出现英文内部分析和 `</think>`，因此不能把该问题归因于 Compass 3.3.0 的内容结构

### 采用的机制

1. ZIP 只保留一个与 Skill 名同名的顶层目录。
2. 主说明采用 `ROUTE → READ → EXECUTE → RESPOND` 短链路。
3. 路由后只读取直接相关的参考资料或脚本，避免全目录扫描。
4. 使用明确的输入、输出、失败降级和验证契约。
5. 分别记录调用、加载、资源读取、业务验证和最终响应证据。

### 没有照搬的内容

- 未复制物理实验领域知识、实验脚本或模型映射表。
- 未硬编码 `/mnt/skills`、scope 或版本目录。
- 未加入 `display-name` 等非标准 SKILL frontmatter 字段。
- 未引入 NumPy、SciPy、python-docx 等无关依赖。
- 未把 README 和比赛说明作为运行依赖打入发布包。
- 未声称单个 Skill 可以自行切换宿主模型。

## 3. 3.3.0 优化内容

### 3.1 平台兼容性

- 发布包从根目录平铺改为 `compass-student-growth/` 单一同名顶层目录。
- 新增 `scripts/validate_platform_package.py`，检查顶层目录、必需文件、名称、版本、重复路径、大小写冲突和路径穿越。
- 新增 `knowledge/platform-runtime.md`，记录平台路由、路径解析、资源选择和状态模型。
- 所有相对路径均以实际加载的 `SKILL.md` 所在目录为基准，不依赖固定 scope 或容器绝对路径。

### 3.2 路由与调用

- 在 frontmatter 描述中补充周计划、时间预算、缓冲、超载、连续失败、疲劳降载、学习复习、职业研究、事实核验和记忆改进等触发词。
- 明确保留简单知识问答、翻译、闲聊等负例，避免过度调用。
- 新增 PLAN、LEARN、RESEARCH、MEMORY、IMPROVE、DIRECT 六条入口。
- 主运行链缩短为 `ROUTE → READ → EXECUTE → RESPOND`。

### 3.3 业务准确性与安全

- 计划场景继续执行时间账本、缓冲区和核心任务上限。
- 疲劳场景增加真实容量、连续失败和 30%–50% 降载规则。
- 市场、薪资、政策等高时效事实继续使用事实门禁；没有可靠来源时必须标记“尚未验证”。
- 最终回复继续禁止内部推理、容器路径、虚假工具调用和未经证实的能力声明。

### 3.4 测试与文档

- 新增 4 个平台包结构测试。
- 新增 4 个平台 E2E 场景定义。
- 本地自动测试总数从 11 增至 16。
- 新增 3.3.0 优化方案、平台运行知识和本测试报告。

## 7. 自动响应安全校验

对 5 个平台最终消息使用 `scripts/validate_response.py` 复核：

| 用例 | `safe` | 检出规则 |
|---|---:|---|
| 显式预算规划 | false | `internal_english`, `think_tag` |
| 自动疲劳降载 | false | `think_tag` |
| 未核验市场事实 | false | `internal_english`, `think_tag` |
| 简单知识负例 | false | `think_tag` |
| 运行知识冒烟 | false | `think_tag` |

因此，“最终输出不包含内部推理”的验收项为 **0/5**，不能标为通过。由于同一泄漏在未调用 Compass 的负例和参考物理实验 Skill 中都能复现，根因更可能位于平台模型推理内容处理、事件流合并或前端最终消息过滤层。该判断是基于现有对照测试的推断，仍需要平台后端日志才能最终定位。

## 10. 下一阶段优化优先级

### P0：修复平台最终输出泄漏

1. 在服务端区分 reasoning 事件与 final 事件，禁止把 reasoning 拼接进最终消息。
2. 最终落库和前端展示前增加 `think` 标签、内部英文句式和容器路径过滤。
3. 发现污染时丢弃污染前缀，只保留标签闭合后的正式答案；不能仅在前端视觉隐藏，数据库持久化内容也必须清理。
4. 用本报告的 5 个用例回归，要求 `validate_response.py` 全部返回 `safe=true`。

该项需要易思捷平台开发方修改输出链路，不能仅靠上传 Skill 文件彻底解决。

### P1：形成真实的脚本执行闭环

1. 为平台 Skill 增加明确的 Python 执行工具映射，而不是只提供文件读取能力。
2. 执行后记录机器可读结果，如 `validation_passed=true`、错误列表和时间账本。
3. 回复只能在执行成功后声称“已通过校验”；执行不可用时明确说明使用了规则人工复核。

### P1：改善疲劳场景的任务语义

1. 复盘任务上限建议设为 0.5–1h。
2. 剩余可执行负荷用于一个最高优先级、可完成的最小行动。
3. 对“很累、连续失败”增加更短的默认输出，避免长篇教育和再次制造压力。

### P1：补充稳定性统计

每个正例、负例至少重复 5–10 次，统计自动调用率、主文件加载成功率、规则通过率、响应安全率、平均响应时间和 P95 响应时间。当前单次用例能证明功能存在，不能替代稳定性统计。

### P2：比赛展示优化

制作一组固定的“输入—路由—资源—机器校验—最终产出”演示证据，将 3.2.0 的 404 与 3.3.0 的正常加载、错误预算与正确预算并排展示。展示重点应放在可量化变化和风险诚实披露，而不是堆叠功能名称。
